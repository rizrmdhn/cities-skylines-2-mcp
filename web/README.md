# CS2MCP web companion

Local web page for the CS2MCP bridge: dashboard, AI activity and a 2D map, plus pause / resume and
speed buttons in the header. Everything else is read-only. See the
[Web companion](../README.md#web-companion) section of the main README for what it does and how
to run it.

- `server/`: the companion server (Node). It serves the built app and forwards two separate
  allowlists under `/api`, adding `CS2MCP_TOKEN` on the server side: read-only GET routes
  (`ALLOWED_ROUTES`) and the control routes (`CONTROL_ROUTES`), which today is exactly one:
  `POST /api/sim/control?speed=0..8&paused=true|false`. Its parameters are validated in the
  companion, nothing else is forwarded, and the POST must carry the companion's own `Origin`
  (browsers always send it; a missing or foreign one is a 403). Every other POST is refused (405)
  before it reaches the game. Adding a control route means editing `CONTROL_ROUTE_PATHS` and
  `CONTROL_ROUTES` in `server/routes.ts`; module load and the tests check both allowlists.
  The game's read-only mode (Options > CS2MCP) makes the bridge refuse the call; the header
  buttons then show as locked. Control calls show up in the game's `/history` like any other
  state-changing call, so they appear on the AI activity page.
- `src/`: the app (React, TanStack Router + Query, shadcn/ui on Base UI). File routes live in
  `src/routes/`; `src/routeTree.gen.ts` is generated by the router plugin.

```powershell
npm run dev     # Vite with the same /api handler, http://127.0.0.1:5173
npm run build   # app into dist/, server into dist-server/
npm start       # serve the build on http://127.0.0.1:8643
npm test        # companion server against a stub bridge, app against a mocked /api (MSW)
```
